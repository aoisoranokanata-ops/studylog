# サンプルJSONの一覧と期待される結果

`spec/schemas/*.schema.json` と合わせて、母艦・子機の双方の受け入れテストに使う。ファイル名の `valid` / `invalid` がそのまま期待結果を表す。

サンプル内の `$comment` キーは**仕様には無い項目**であり、前方互換（知らない項目は無視する／仕様書 第1章-5）の確認も兼ねている。受信側はこのキーを無視して正常に処理できること。

## 正常例

| ファイル | 内容 | 期待される結果 |
|---|---|---|
| `down-01-full-valid.json` | `full`。masters・quotas 3件・reviews 2件・summary あり | 子機は masters を丸ごと置き換え、ノルマ3件・復習2件・週サマリを表示する |
| `down-02-lite-valid.json` | `lite`（QR相当）。masters 無し、quotas 2件、`acks` 1件 | masters は手元のものを維持。ノルマは `labels` で表示できる。up-01 が取り込み済みになる |
| `down-03-acks-valid.json` | `quotas: []`、`reviews: null`、`summary` はキー自体が無い、`acks` 1件 | ノルマは空、復習はクリア、**週サマリは前回の内容を維持**。ack処理は下表のとおり |
| `up-01-normal-valid.json` | 2026-09-20 18:30 送信。セッション2・誤答1・復習結果1・達成状況2 | 母艦が6件を追加取り込み。未分類0件 |
| `up-02-resend-valid.json` | 2026-09-21 19:00 送信。up-01 の6件を再送＋新規2件 | **再取り込みしても件数が増えない**。4e000002 のみ `updatedAt` が新しいので更新。差分は追加2・更新1・スキップ5 |
| `up-03-unclassified-valid.json` | down-03 受信後の送信。未分類・未知のマスタID・取り消し済みを含む | 全件受け入れ。**未分類2件**（4e000005、4e000006）として分類画面に出る。4e000004 は削除扱い |

## 異常例

| ファイル | 違反の内容 | 期待される結果 |
|---|---|---|
| `invalid-down-01-future-version.json` | `schemaVersion: 2` | 「アプリの更新が必要です」と表示して中止（スキーマ検証より前に判定） |
| `invalid-down-02-missing-required.json` | `full` なのに `masters` 無し／`quotas[0]` に `targetSeconds`・`labels` 無し／`settings.weekStartsOn` 無し | パッケージ全体を拒否。欠落した項目名を示す |
| `invalid-down-03-bad-formats.json` | タイムゾーン無しの `createdAt`／日付・色の書式違反／`type` が定義外／`dayChangeHour` が範囲外 | パッケージ全体を拒否 |
| `invalid-up-01-type-violation.json` | `activeSeconds` が文字列／`focus` が範囲外／`deleted` が文字列／`entryMode`・`reason` が定義外／`records.quotaStatus` 欠落 | パッケージ全体を拒否。`rejected/` に移動し理由を記録 |
| `invalid-up-02-unclassified-conflict.json` | `unclassified: false` なのに `examId` が `null` | パッケージ全体を拒否 |
| `invalid-up-03-app-level-checks.json` | JSON Schema は通るが `includedIds` 不一致／`from > to`／`activeSeconds` 過大／`correct > attempted` | **アプリ側の検証で**拒否（仕様書 付録B）。スキーマ検証だけで通してはいけない |

## サンプルが表現している時系列（ack と再送の確認用）

```
09-20 07:10  down-01（full）を子機が受信
09-20 09:05〜18:20  子機で計測・誤答・復習・達成状況を記録
09-20 18:30  up-01 を送信（c0000001、6件）
09-21 06:55  down-02（lite、acks: [c0000001]）を受信
             → 4e000001・6f000001・8a000001・2b000001・2b000002 が取り込み済み
             → 4e000002 は 09-21 08:00 に編集したため、この時点では ack より後の
                編集ではないが、送信時刻(09-20 18:30) より後の編集なので未取り込みのまま
09-21 14:00〜17:45  さらに記録（4e000003、4e000004、2b000003）
09-21 19:00  up-02 を送信（c0000002、8件＝未取り込み分をすべて累積送信）
09-21 20:00  2b000004 を記録（down-02 のノルマ 9c000005 の達成状況）
09-21 21:10  4e000003 を編集（＝up-02 の送信時刻より後）
09-22 07:00  down-03（acks: [c0000001]）を受信
             → 母艦はまだ up-02 を取り込んでいないので、c0000002 は ack されない
             → 4e000002・4e000003・4e000004・2b000003 は未取り込みのまま
09-22 09:50〜14:20  さらに記録（4e000005 未分類、4e000006 未知のマスタID）
09-22 18:00  up-03 を送信（c0000003、8件）
```

このうち、受け入れ条件として特に確認すべき点：

1. **再送しても増えない**：`up-01` → `up-02` の順に取り込んでも、母艦の総件数は 8 件（`up-02` の `includedIds` と同じ）にとどまる
2. **送信後に編集した記録は未取り込みのまま**：`4e000003` は `up-02` に含まれていても、`updatedAt(21:10) > 送信時刻(19:00)` なので `c0000002` が ack されても未取り込み
3. **ackを受け取らない限り消えない**：`c0000002` が ack されない限り、`4e000003`・`4e000004`・`2b000003` は何日経っても子機に残る
4. **母艦の編集が守られる**：母艦で `4e000001` を編集（`updatedAt` を 2026-09-23 に）した後に `up-02` を再取り込みしても、母艦の内容は変わらない
5. **未分類として受け入れる**：`4e000006` の `examId` は masters に無いが、拒否せず未分類にする
6. **ノルマが消えても達成状況は残る**：`down-03` で `quotas: []` になった後も `2b000004`（9c000005 の達成状況）は送信対象として残る
